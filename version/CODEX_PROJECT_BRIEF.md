# CODEX_PROJECT_BRIEF.md

## Purpose of this file

This file gives Codex the complete project context and implementation direction for the Web-Technologien final project. Codex should read this file before making any code changes.

The project is a small API-first web application for managing a to-do list. It must include:

- a frontend,
- a backend,
- a simple data storage layer,
- a REST/HTTP API,
- an OpenAPI description created before or together with the implementation.

## Course context and fixed requirements

This is a final project for the course **Web-Technologien**.

Important requirements from the course slides:

1. The project should follow an **API-first** approach.
2. Requirements should be described with **User Stories**.
3. The API concept should define:
   - resources,
   - endpoints,
   - HTTP methods,
   - request and response data types,
   - status codes and error responses.
4. The project should include an **OpenAPI Description**, preferably `openapi.yaml`.
5. Swagger tools such as Swagger Editor or Swagger UI may be used for API documentation and testing.
6. The backend framework must be chosen from:
   - **Flask (Python)**, or
   - **NestJS (JavaScript / TypeScript)**.

For this project, use **Flask (Python)**.

Do **not** use Express.js as the final backend framework, because the course framework choices are Flask or NestJS.

## Chosen technology stack

Use the following stack unless the user explicitly requests a change:

- **Backend:** Flask with Python
- **Database:** SQLite
- **Frontend:** HTML, CSS, vanilla JavaScript
- **API specification:** OpenAPI 3.0 in `openapi.yaml`
- **API documentation / testing:** Swagger UI or Swagger Editor

Reasoning:

- Flask is simple and sufficient for a small REST API.
- SQLite is a real but lightweight database and is easy to use with Python.
- Vanilla HTML/CSS/JS is enough for the frontend and avoids unnecessary complexity.
- OpenAPI demonstrates the API-first requirement clearly.

## Project goal

Build a web application called **To-do Listen Verwaltung**.

The user should be able to manage to-do entries in a browser. The frontend communicates with the Flask backend through a REST API. The backend stores data in SQLite.

The project should remain small, understandable, and easy to present in a roughly 7-minute course presentation.

## Main user stories

### User Story 1: Create a task

As a user, I want to create a new to-do task so that I can save things I need to do.

Acceptance criteria:

- A task must have a title.
- A task may have an optional description.
- A task may have an optional due date.
- A task may have a priority.
- Newly created tasks are stored in the database.
- Newly created tasks appear in the frontend list.

### User Story 2: View all tasks

As a user, I want to see all my tasks in a list so that I can get an overview of my work.

Acceptance criteria:

- The frontend displays all tasks returned by the API.
- Each task shows at least title and completion status.
- Optional fields such as description, due date, and priority should be shown if available.

### User Story 3: Edit a task

As a user, I want to edit an existing task so that I can correct or update its content.

Acceptance criteria:

- The user can update title, description, due date, and priority.
- The backend validates the data.
- The updated task is stored in SQLite.
- The frontend refreshes the changed data.

### User Story 4: Mark a task as done or not done

As a user, I want to mark tasks as completed or open so that I can track my progress.

Acceptance criteria:

- The user can toggle the `completed` state.
- The new status is stored in the database.
- Completed tasks are visually distinguishable in the frontend.

### User Story 5: Delete a task

As a user, I want to delete tasks that I no longer need so that my list stays clean.

Acceptance criteria:

- The user can delete a task.
- The deleted task is removed from the database.
- The frontend no longer displays the deleted task.

### Optional user story: Filter tasks

As a user, I want to filter tasks by status so that I can focus on open or completed work.

Acceptance criteria:

- The user can view all tasks.
- The user can view only open tasks.
- The user can view only completed tasks.

## Data model

Use one main resource: `Todo`.

Recommended fields:

```json
{
  "id": 1,
  "title": "Web-Technologien Projekt vorbereiten",
  "description": "OpenAPI, Flask backend und Frontend erstellen",
  "completed": false,
  "dueDate": "2026-05-20",
  "priority": "high",
  "createdAt": "2026-05-17T12:00:00Z",
  "updatedAt": "2026-05-17T12:00:00Z"
}
```

Field details:

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | integer | yes | Primary key, generated by database |
| `title` | string | yes | Must not be empty |
| `description` | string | no | Optional text |
| `completed` | boolean | yes | Default: `false` |
| `dueDate` | string/date | no | Format: `YYYY-MM-DD` |
| `priority` | string | no | Suggested values: `low`, `medium`, `high` |
| `createdAt` | string/datetime | yes | Generated on creation |
| `updatedAt` | string/datetime | yes | Updated on changes |

Use snake_case column names in SQLite if preferred, but API JSON should use camelCase consistently.

## API-first design

Create or update `backend/openapi.yaml` before or alongside backend implementation.

The implementation must follow the OpenAPI specification.

### Required endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| `GET` | `/api/health` | Simple health check |
| `GET` | `/api/todos` | Get all tasks |
| `GET` | `/api/todos/{id}` | Get one task by ID |
| `POST` | `/api/todos` | Create a new task |
| `PUT` | `/api/todos/{id}` | Replace/update a whole task |
| `PATCH` | `/api/todos/{id}` | Partially update a task, especially completion status |
| `DELETE` | `/api/todos/{id}` | Delete a task |

### Optional query parameters for `GET /api/todos`

Support these only if implementation time allows:

- `status=all|open|completed`
- `priority=low|medium|high`
- `q=<search text>`

### Important status codes

Use meaningful HTTP status codes:

| Status code | Meaning |
|---|---|
| `200 OK` | Successful GET, PUT, PATCH |
| `201 Created` | Successful POST |
| `204 No Content` | Successful DELETE |
| `400 Bad Request` | Invalid input data |
| `404 Not Found` | Todo does not exist |
| `500 Internal Server Error` | Unexpected server error |

### Error response format

Use a consistent JSON error format:

```json
{
  "error": "ValidationError",
  "message": "Title is required."
}
```

## Backend implementation guidelines

Use Flask.

Recommended dependencies in `backend/requirements.txt`:

```text
Flask
flask-cors
PyYAML
```

Optional dependency if adding Swagger UI directly to Flask:

```text
flask-swagger-ui
```

Backend requirements:

1. Provide the REST API under `/api/...`.
2. Use SQLite for persistent storage.
3. Create the `todos` table automatically if it does not exist.
4. Use parameterized SQL queries to avoid SQL injection.
5. Validate input data:
   - `title` is required for create and full update.
   - `title` must not be empty.
   - `completed` must be boolean if provided.
   - `priority` should be one of `low`, `medium`, `high` if provided.
6. Return JSON responses.
7. Enable CORS so that the frontend can call the backend.
8. Keep the code simple and understandable for presentation.

Suggested SQLite schema:

```sql
CREATE TABLE IF NOT EXISTS todos (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    description TEXT,
    completed INTEGER NOT NULL DEFAULT 0,
    due_date TEXT,
    priority TEXT DEFAULT 'medium',
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

## Frontend implementation guidelines

Use plain HTML, CSS, and JavaScript.

The frontend should:

1. Display all tasks from `GET /api/todos`.
2. Provide a form to create a new task.
3. Allow toggling the completion status.
4. Allow editing a task.
5. Allow deleting a task.
6. Show basic error messages if an API call fails.
7. Optionally provide filters for all/open/completed tasks.

The frontend must communicate with the backend through `fetch()` calls to the REST API.

Do not store the main data only in the frontend. The database/backend must be the source of truth.

## Validation checklist

After implementation, Codex must check:

### Backend checks

- `python -m compileall backend` passes.
- Flask app starts without errors.
- `GET /api/health` returns success.
- `GET /api/todos` returns JSON.
- `POST /api/todos` creates a todo.
- `PATCH /api/todos/{id}` can update `completed`.
- `PUT /api/todos/{id}` can update a todo.
- `DELETE /api/todos/{id}` removes a todo.
- Invalid input returns `400`.
- Unknown ID returns `404`.

### Frontend checks

- Page loads without console syntax errors.
- The frontend can load todos from the backend.
- Creating a todo works.
- Toggling completion works.
- Editing works.
- Deleting works.
- Error messages are understandable.

### Documentation checks

- `openapi.yaml` matches the implemented endpoints.
- `README.md` contains startup instructions.
- The chosen stack is clearly stated as Flask + SQLite + vanilla frontend.

- ignore the OpenAPI file,
